# 06. Заказы

> Статус: Документация готова
> Версия: 0.1
> Связанные документы: [03. Интеграция с API](03-api-integration.md), Backend [05. Заказы](../../backend/05-orders.md)

## 1. Список заказов (`/orders`)

AntD Table над `GET /admin/orders?status=&page=&size=`.

Колонки: номер (`ORD-2026-000123`, моно), статус (цветной Tag), клиент
(имя + телефон), город доставки, сумма (`totalCents`), создан (локальное
время из ISO UTC), действие «Открыть».

Фильтр по статусу — сегментированные табы над таблицей:
**Все | Новые (NEW) | Подтверждённые (CONFIRMED) | Доставленные (DELIVERED) | Отменённые (CANCELLED)**.
Значение синхронизируется с query-параметром URL (`/orders?status=NEW`) —
ссылку можно шарить.

Цвета статусов: NEW — blue, CONFIRMED — gold, DELIVERED — green,
CANCELLED — red.

Сортировка серверная по дате создания (новые сверху); клиентская сортировка
колонок не применяется.

## 2. Карточка заказа (`/orders/:id`)

Descriptions-панель:

- Номер, статус, создан.
- Получатель: имя, телефон.
- Доставка: город, адрес, комментарий.
- Финансы: товары (`itemsTotalCents`), доставка (`deliveryCents`), итого.

### Блок «Состав заказа»

> ⚠️ Блокер UX [03 §6.3]: в текущем API у оператора нет позиций заказа
> (`AdminOrderResponse` без `items`, детального эндпоинта нет). До расширения
> бэкенда блок показывает заглушку «Состав появится после обновления API» и
> кнопку «Обновить». Ожидаемый контракт уже описан — UI подключит его одной
> мутацией хука.

### История статусов

Аналогично составу — ждём расширение (`statusHistory` уже есть в
пользовательском контракте). В v1 показываем только текущий статус.

## 3. Смена статуса

Действия в шапке карточки и в строке таблицы (быстрое действие):

| Текущий | Доступные действия |
|---|---|
| NEW | Подтвердить → CONFIRMED; Отменить → CANCELLED |
| CONFIRMED | Отметить доставленным → DELIVERED; Отменить → CANCELLED |
| DELIVERED | — (терминальный) |
| CANCELLED | — (терминальный) |

Правила:

1. UI показывает только допустимые переходы (матрица бэкенда); сервер всё
   равно валидирует — `409` при недопустимом переходе показываем как
   notification c `detail` и рефетчим карточку (статус мог измениться у
   другого оператора).
2. Отмена — через `Modal.confirm`: «Заказ №… будет отменён. Остатки вернутся
   на склад. Действие необратимо.»
3. После мутации — invalidate `['orders']`, `['order', id]`, `['stats']`;
   тост успеха («Заказ подтверждён»).
4. Повторный PATCH с тем же статусом безопасен: бэкенд возвращает заказ без
   изменений (idempotent no-op).

## 4. Поиск и сценарии оператора

v1: поиск по номеру заказа не предусмотрен бэкендом (фильтр только по
статусу). Типовой сценарий — фильтр NEW, обработка по очереди: открыть →
проверить реквизиты → подтвердить; после передачи в доставку — отметить
доставленным. Пагинация стандартная (page/size ≤100).

## 5. Краевые случаи

- Заказ отменён покупателем параллельно → PATCH вернёт `409`; после рефетча
  таблица покажет актуальный статус.
- Комментарий клиента может отсутствовать — поле скрывается.
- Суммы отображаются из полей бэкенда, ничего не пересчитываем на клиенте.
