# 09. Отзывы (блок 9)

Зависит от: блок 6 (детальная страница товара), блок 7 (право на отзыв = DELIVERED-заказ).

Документ-план перед реализацией. Опирается на фактический контракт бэкенда
(`ReviewController` / `ReviewService` / `Review`), чтобы фронт не предполагал того,
чего бэкенд не делает.

---

## 1. Контракт бэкенда (источник истины)

| Метод | Путь | Доступ | Ответ / ошибки |
|---|---|---|---|
| `GET` | `/products/{productId}/reviews?page&size` | **Публичный** (`permitAll` на GET `/api/v1/products/**`) | `200 PageResponse<PublicReviewResponse>`; только `moderated=true`, сортировка `createdAt DESC`; `size` клампится `[1..100]` |
| `POST` | `/products/{productId}/reviews` | токен | `201 ReviewResponse` + Location; **409** — отзыв этого пользователя на товар уже есть; **403** — нет DELIVERED-заказа с этим товаром; **404** — товара нет; **400** — валидация (Problem Details `errors`) |
| `PATCH` | `/reviews/{id}` | токен, только владелец | `200 ReviewResponse`; чужой/несуществующий id → **404**; `rating` и `text` независимы и опциональны |
| `DELETE` | `/reviews/{id}` | токен, только владелец | `204`; чужой/несуществующий id → **404** |

Админские эндпоинты (`GET /admin/reviews`, `PATCH /admin/reviews/{id}/moderation`) — вне скоупа мобильного.

### DTO

```jsonc
// PublicReviewResponse — элемент публичного списка
{ "id": "uuid", "userFirstName": "Анна" | null, "rating": 5, "text": "…", "createdAt": "ISO" }

// ReviewResponse — ответ на create/update (владельцу)
{ "id": "uuid", "productId": "uuid", "rating": 5, "text": "…", "moderated": false, "createdAt": "ISO" }
```

### Валидация

- `rating`: create — обязателен, int 1..5; update — опционален.
- `text`: `@Size(min=1, max=2000)`, **null валиден** → отзыв может состоять из оценки без текста;
  пустая строка невалидна (фронт шлёт поле только если есть непустой текст).

### Важные нюансы серверной логики

1. **Модерация**: новый отзыв сохраняется с `moderated=false` и НЕ появляется в публичном
   списке, пока админ не одобрит. Ответ create это честно отражает (`moderated:false`)
   → UI обязан показывать статус «На модерации».
2. **Редактирование не сбрасывает модерацию** — опубликованный отзыв остаётся видимым
   после правки (и рейтинг пересчитывается).
3. Право на отзыв проверяется сервером по наличию DELIVERED-заказа, содержащего товар
   (`findDeliveredPurchases`).
4. Чего **нет** на бэкенде:
   - «мой отзыв на товар» (`GET /reviews/my`, параметра `mine=true`);
   - precheck права («могу ли я оставить отзыв»);
   - `productId` внутри позиций заказа (только `skuId`/`article`) → фронт не может даже
     косвенно вычислить право из своей истории заказов.

## 2. Следствия для фронта (решения)

1. **Право на отзыв не предвычисляем** (технически невозможно) — кнопка/форма «Написать
   отзыв» показывается всем авторизованным без своего отзыва на этот товар; серверные
   403/409 разворачиваются в понятные локализованные тосты:
   - 403 → «Оставить отзыв могут покупатели, получившие заказ»;
   - 409 → «Вы уже оставляли отзыв на этот товар» (+ сброс локального состояния формы);
   - 404 при edit/delete → считаем отзыв удалённым (админ/другое устройство), чистим
     локальную запись, возвращаем к состоянию «написать отзыв».
2. **Свой отзыв трекаем локально**: `Map<productId, MyReview>` (id, rating, text,
   moderated, createdAt), персист в kvStorage ключом `reviews.my:{userId}` — паттерн
   кэша избранного из блока 8. Иначе после перезапуска негде взять id отзыва для
   PATCH/DELETE. Записи обновляются только ответами сервера (create/update/delete);
   расхождение (отзыв удалён на другом устройстве) лечится через 404-ветку выше.
3. **Гость** — только чтение списка + строка-приглашение «Войдите, чтобы оставить
   отзыв» → тост (как у избранного). Кнопки форм для гостя скрыты.
4. Список подгружается страницами по 10, догрузка кнопкой «Показать ещё» (секция живёт
   внутри ScrollView детальной страницы — вложенный скролл не используем).

```
│   └── index.ts
├── core/bootstrap/
│   └── reviews-session-sync.ts      # init(userId)/reset() по сессии (как блок 8)
├── shared/ui/star-rating-input/     # интерактивные звёзды (общие для create/edit)
├── features/
│   ├── write-review/ui/             # форма создания (звёзды + текст)
│   ├── edit-review/ui/              # форма редактирования (prefill)
│   └── delete-review/ui/            # кнопка + Alert-подтверждение
└── widgets/product-reviews/ui/      # секция на детальной: сводка, мой отзыв, список
```

Границы соблюдены: звёзды — в shared (feature→feature импорт запрещён); виджет собирает
фичи (widgets→features разрешено); entities/review знает только shared.

## 4. UI/UX

- Секция «Отзывы» на детальной странице товара (после характеристик): заголовок с
  количеством, сводка (средний балл + звёзды из `product.ratingAverage/ratingCount`
  — данные уже приходят с товаром).
- Карточка отзыва: имя (`userFirstName` ?? «Покупатель»), звёзды, дата
  (Intl по текущей локали), текст.
- Свой отзыв — карточка с чипом статуса («Опубликован»/«На модерации») и действиями
  Изменить/Удалить; формы create/edit раскрываются инлайн, submit с индикатором.
- Тосты на успех: создан («Отзыв отправлен, появится после проверки»), обновлён,
  удалён. Ошибки — тосты по п.2.1 (локализованные, не сырой detail бэкенда).

## 6. Критерий приёмки

- [ ] Любой (в т.ч. гость) читает отзывы на детальной странице, пагинация работает.
- [ ] Покупатель с полученным заказом оставляет отзыв; до модерации видит чип
      «На модерации», после — отзыв появляется в общем списке.
- [ ] Автор может изменить и удалить свой отзыв; после перезапуска приложения его
      отзыв всё ещё отображается как «его» (локальный кэш) и остаётся редактируемым.
- [ ] Не-покупатель получает понятное сообщение (403), повторная попытка — 409 с
      понятным сообщением; сырые английские detail бэкенда в UI не светятся.
- [ ] Рейтинг товара на карточках пересчитывается сервером — фронту делать нечего.
